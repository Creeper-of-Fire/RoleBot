01 / OVERVIEW

赛季生命周期（if-else，不是状态机）

bot 不维护状态字段——投稿期判断 = start_date <= today <= end_date（一个 if-else）。admin 改 toml 即可调整时间窗，立即生效。

bot 不做的事——投票、身份组设计、forum 帖子自动识别、胜负判断、自动发面板、管理投稿 / 取缔资格、最终身份组（winner_role）发放、身份组过期提醒 / 自动回收、游客领取面板。这些由管理组 + 委员会 + 其他 bot 负责。
unix 哲学核心——bot 提供最少工具（投稿面板 + 主入口面板 + 撤销投稿 + grant_honor）；身份组回收、winner_role 发放、胜负判断、状态机切换、过期提醒全部由 admin / 委员会负责。
02 / PREPARATION

准备工作清单

第一次启用一个 guild 时，按顺序完成这些事。已完成的事可以跳过。

AdminDiscord 端操作

  1. 创建 3 个频道（主入口 + A 组分区 + B 组分区），见 §3
  2. 创建 4 个 Discord 身份组（见下方表格），记下 ID
  3. 把 bot 邀请到服务器，授予 manage_roles 权限

Bot通过命令操作

  1. 合战丨配置 下载配置 拿当前 toml + SHA-256
  2. 用文本编辑器修改 toml（见 §4 字段详解）
  3. 合战丨配置 上传配置 + 粘上 SHA-256 前 12 字符

4 个必需身份组（简化版）

身份组数量用途
A 组支持者1用户点 A 按钮后 bot add；过期 / 移除由 admin 手动到 Discord 处理（bot 不推提醒）
B 组支持者1同上
A 组参赛者1用户投 A 后 bot add；过期 / 移除由 admin 手动到 Discord 处理
B 组参赛者1同上
最终身份组（winner_role）不在这里管——bot 完全不参与 winner_role 发放。委员会走 7+7 人工流程后，admin 手动到 Discord 给获胜方 supporter add winner_role（持续到下次合战结束）。
游客领取——bot 不发游客面板（游客身份由 admin 用 honor claimable 模块或 Discord 手动 add）。
03 / CHANNELS

频道设置 + 权限

bot 不管频道权限——所有可见性由 Discord 端管理组设置。如果分区权限没设好，所有人（包括对方阵营）都能看到——这是 admin 的责任。

主入口频道
所有人可见
A 组 / B 组 阵营选择按钮
A 组分区
仅 A 组阵营可见
📨 投稿按钮 + A 组推广
B 组分区
仅 B 组阵营可见
📨 投稿按钮 + B 组推广

权限示例（A 组分区）

@everyone       → ❌ view_channel
@A 组支持者身份组 → ✅ view_channel
@Bot 角色        → ✅ view_channel + send_messages + manage_messages
权限出错怎么办？检查 Discord 端频道权限覆盖 + bot 的角色权限。如果 bot 在某频道没有 view_channel，发消息会失败但不会报错。

05 / SEASON FLOW

赛季流程命令

简化版：4 个核心命令——admin 手动发面板 + 撤销投稿（bot 按 toml 时间 if-else 判断投稿期，bot 投稿后自动 grant_honor）。

  1. 发送主入口面板 main
    /合战丨核心 发送面板 channel_key:main
    发 A 组 / B 组 互斥领取按钮 + 两阵营统计到主入口频道。channel_key 自动补全。
  2. 发送分区投稿面板（每个阵营各一次）
    /合战丨核心 发送面板 channel_key:faction_a
    /合战丨核心 发送面板 channel_key:faction_b
    发 📨 投稿按钮 + 该阵营 random 几个投稿。分区频道由 submission_channel_id 决定。
  3. 撤销投稿（admin 命令）
    /合战丨核心 撤销投稿 submission_id=<UUID>
    从 json 删除该投稿（不 remove contributor_role，不 撤销 honor）。如需撤销身份组 / honor，admin 自己处理。
  4. 投稿成功后 bot 自动 grant_honor
    不用命令——bot 在用户投稿成功后自动调 honor 系统的 grant_honor(member.id, contributor_honor_uuid)。前提：honor toml 已配对应 UUID + creative_battle toml 引用（见 §6）。
channel_key 自动补全——输入 fac 会自动建议 faction_a / faction_b / main。
互斥领取——用户已选 A 后点 B，bot 拒绝加入并提示"如需更换请联系管理组"。bot 不 remove A 的 supporter_role（unix 哲学：身份组生命周期由 admin 管）。

赛季结束后动作（跨模块配合）

创作大会 不只靠 creative_battle 模块自己——cup_honor 和 honor 系统都会参与。下方是完整时间线：

start ~ end_date] -->|end_date 到
bot 不再接受| B[投稿期结束] B -->|now >= cup_honor
expiration_date| C[HonorExpirationCog 推提醒
notification 频道] C -->|admin 手动| D[remove contributor_role] D -->|胜负判断
人工 7+7| E[winner_role
人工 add] classDef active fill:#ddeae5,stroke:#2f6f5e,color:#14171e classDef inactive fill:#e9e3d6,stroke:#7c7a72,color:#14171e classDef gate fill:#f0e9d8,stroke:#c97b3f,color:#14171e class A active class B gate class C inactive class D inactive class E inactive
  1. 投稿期结束（自动）
    bot 按 end_date 自动停止接受投稿（if-else 判断）。推广面板也停止更新。supporter_role / contributor_role 仍然挂在用户身上，bot 不主动 remove。
  2. HonorExpirationCog 推过期提醒（cup_honor 通用机制）
    投稿成功后 bot 调用的那个 honor toml 配顶层 expiration_date 字段。到时间后，HonorExpirationCog 的 expiration_check_loop（24h 轮询）自动推 ExpiredHonorNoticeView embed 到 honor toml 的 cup_honor.notification.channel_id 频道。
  3. admin 手动 remove contributor_role
    看到 HonorExpirationCog 推的提醒后，admin 到 Discord 身份组设置 → 找到 contributor_role → 手动 remove 所有持有成员。同时可点 embed 上的"补发 honor（按 role 持有者）"按钮（HonorExpirationCog 内置健康检查）。
  4. 人工流程：决定胜负方 + 7+7 设计投稿投票
    admin 看 data/creative_battles_*.json 决定胜负方 → 委员会 7 天自由投稿 + 7 天投票 + 设计要求审核 → 设计确定后 admin 手动到 Discord 给获胜方所有 supporter add winner_role（持续到下次合战结束）。
  5. admin 手动 remove supporter_role
    admin 自己定时间（赛季结束 / 一周后 / 一月后），到 Discord 身份组设置 → 手动 remove 所有 supporter。cup_honor 不监控 supporter_role（它只管 cup_honor 类型 honor）。
为什么用 HonorExpirationCog 通用机制？honor toml 的顶层 expiration_date 字段 + HonorExpirationCog 的 expiration_check_loop（24h 轮询）+ ExpiredHonorNoticeView——任何 honor 都可用，db 不存过期时间。creative_battle 不用自己写 expire 逻辑。unix 哲学：复用现有工具。
06 / HONOR INTEGRATION

永久贡献者荣誉（bot 自动 grant_honor）

简化版：bot 在投稿成功后直接调 honor 系统的 grant_honor 接口。uuid 在 creative_battle toml 配，从 honor toml 引用。

步骤 1

honor toml 加 [[definitions]] + 顶层 expiration_date 字段

用 荣誉头衔丨配置 下载配置 拿 honor toml，加 2 个 [[definitions]] 块（每个阵营一个）。每个 honor 加顶层 expiration_date 字段（HonorDefinitionItem 直接属性）——HonorExpirationCog 的 24h 轮询会自动监控到期 + 推提醒。db 不存过期时间——过期时间只在 toml 配置层。

[[definitions]]
uuid = "<UUID v4 即可，或用 生成UUID 命令>"
name = "🍃 A 组之贡献者"
description = "参与创作大会·A 组投稿"
role_id = 222222222    # = A 组 contributor_role_id
hidden_until_earned = true

expiration_date = "2026-12-31T23:59:59+08:00"   # ★ 顶层字段——HonorExpirationCog 监控过期 + 推提醒
expiration_date = "2026-12-31T23:59:59+08:00"
lead_days = 3

[[definitions]]
uuid = "<另一个 UUID>"
name = "🍃 B 组之贡献者"
description = "参与创作大会·B 组投稿"
role_id = 666666666
hidden_until_earned = true

expiration_date = "2026-12-31T23:59:59+08:00"   # ★ 顶层字段
expiration_date = "2026-12-31T23:59:59+08:00"

creative_battle toml 引用 UUID

把 honor UUID 填到对应阵营的 contributor_honor_uuid。

contributor_role_id = 222222222       # = honor toml 里的 role_id
contributor_honor_uuid = "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee"

[[factions]]
key = "faction_b"
contributor_role_id = 666666666
contributor_honor_uuid = "11111111-2222-3333-4444-555555555555"
步骤 3

bot 自动处理

赛季内：用户投稿 → bot 自动 add_roles(contributor_role_id) + 自动 grant_honor(member.id, contributor_honor_uuid)。无需 admin 操作。

失败处理：grant_honor 失败不阻断投稿——json 标记 honor_granted=false，admin 看到后手动到 honor 系统补。

过期处理：到 顶层 expiration_date 字段 后，HonorExpirationCog.expiration_check_loop（24h 轮询）自动推 ExpiredHonorNoticeView 到 honor toml 的 cup_honor.notification.channel_id 频道 → admin 看到后手动 remove contributor_role。

UUID 命令只是方便工具——任何恰当熵池（如 uuid.uuid4() 输出）都行，不会跟现有 record 冲突。命令的好处是手机上点一下复制。
撤销投稿不撤销 honor——bot 的 /合战丨核心 撤销投稿 命令只删 json，不撤销已授予的 honor。如需撤销，请到 honor 系统的 /荣誉头衔丨管理 管理持有者 处理。
07 / ROLE RECLAIM

身份组回收（HonorExpirationCog 推提醒 + admin 手动 remove）

contributor_role 用 honor 系统的顶层 expiration_date 字段（HonorDefinitionItem 直接属性）——HonorExpirationCog（独立 cog）24h 轮询自动监控到期 + 推提醒到 honor toml 的 cup_honor.notification.channel_id 频道。admin 看到提醒后手动到 Discord remove contributor_role。bot 不调 remove_roles（unix 哲学）。

身份组何时过期 / 回收谁推提醒谁 remove / add
A 组 / B 组 contributor_rolehonor toml 的顶层 expiration_date 字段HonorExpirationCog 自动（24h 轮询检查）admin 手动（看到提醒后到 Discord remove）
A 组 / B 组 supporter_roleadmin 自己定（赛季结束后 / 比赛结算后）无（HonorExpirationCog 不监控 supporter_role）admin 手动
最终身份组（winner_role）admin 走 7+7 人工流程后手动 add winner_role；下次合战结束时手动 remove无admin 手动（add + remove）
HonorExpirationCog 自动推的提醒长什么样？ExpiredHonorNoticeView embed——含 honor 名称 + 过期时间 + 当前持有该身份组成员数 + "bot 不调 remove_roles——admin 看到后手动 remove"提示。详细实现见 honor_system/honor_expiration_cog.py。
为什么 contributor_role 用 HonorExpirationCog，但 supporter_role 不用？supporter_role 的回收时机完全由 admin 决定（比赛结束？一周后？一个月后？永久保留？），bot 硬编码任何"几月后"规则都是过度防御。contributor_role 跟赛季强绑定——赛季结束 = 应过期——所以借力 HonorExpirationCog 的"按时间戳过期 + 推提醒"能力（cup_honor 类型 honor）。

winner_role 发放（admin 全权）

赛季结束后，admin 决定胜负方 + 走 7+7 人工流程。设计确定后：

  • 到 Discord 身份组设置 → 找到 winner_role → 手动 add 给获胜方所有 supporter
  • 下次合战结束时手动 remove winner_role

完整真起测试清单

Pre-flight

  1. 确认 config.py 里 COGS 包含 "creative_battle"（v2 默认 enabled=False，测试时手动改 True）
  2. 本地测试服务器建 3 个频道（主入口 + 两个分区）+ 4 个身份组（见 §2）
  3. 设置 Discord 端频道权限（见 §3）

Toml 配置

  1. 编辑本地 data/creative_battle_<test_guild_id>.toml（参考 §4 示例，把所有 ID 换成测试服务器的）
  2. 通过 合战丨配置 上传配置 上传（首次可省略 hash）
  3. 如果走永久贡献者荣誉流程，同时在 honor toml 加 2 个 [[definitions]]（每个加顶层 expiration_date 字段），并在 creative_battle toml 填 contributor_honor_uuid 引用。db 不存过期时间——无需 alembic 迁移。

启动 bot

  1. python main.py 启动 bot，看启动日志确认 CreativeBattleCog 注册成功
  2. 确认 bot 已加入测试服务器，斜杠命令出现在聊天框
  3. 把 config.py 的 creative_battle.enabled 改成 True + 编辑 toml 把 start_date 改成今天，验证投稿可正常走通

按钮交互测试

用第二个 Discord 账号（或测试服务器里建一个 dummy 用户）测以下流程：

  1. 跑 合战丨核心 发送面板 channel_key:main → 主入口收到 A 组 / B 组 按钮
  2. 点 A 组 → 拿到 A 组支持者身份组 + 收到 ephemeral 确认
  3. 互斥测试：已选 A 后点 B 组 → bot 应拒绝并提示"你已在 A 组，如需更换请联系管理组"，A 角色不被 remove
  4. 跑 合战丨核心 发送面板 channel_key:faction_a → A 组分区收到 📨 按钮
  5. 点 📨 → 弹 Modal → 填标题 + 描述 → 提交 → 拿到 A 组参赛者身份组 + 自动 grant_honor
  6. 重复 4-5 步（让另一个 dummy 用户加 B 组 + 投稿）
  7. 等 5 分钟看推广 embed 是否 refresh（promotion.refresh_minutes 默认 5，仅投稿期内刷新）
  8. 撤销投稿测试：拿到 submission_id（从 data/creative_battles_*.json 里读）→ 跑 合战丨核心 撤销投稿 submission_id=... → json 应删除该投稿，contributor_role 不被 remove

投稿期外测试（简化版：if-else）

  1. 投稿期结束测试：编辑 toml 把 end_date 改成昨天 → 用户点 📨 → bot 应拒绝"当前不是投稿期"。不需要重启 bot——下一条投稿请求立即用新时间。
  2. 推广面板停止更新测试：投稿期外等 5 分钟 → 推广 embed 不应再 refresh（但消息本身还在频道里）
  3. 身份组回收测试：bot 不做任何 remove 操作。admin 手动到 Discord 身份组设置 → remove 成员。验证人工流程跑通。
  4. 最终身份组测试：bot 不参与——admin 手动到 Discord 给获胜方所有 supporter add winner_role（验证人工 7+7 流程）
  5. grant_honor 验证：投稿后到 honor 系统查 /荣誉头衔丨管理 或用户荣誉墙，确认投稿用户已持有 🍃 A/B 组之贡献者 honor
  6. HonorExpirationCog 过期提醒测试：把 honor toml 的 顶层 expiration_date 字段 改成今天 → 等 HonorExpirationCog.expiration_check_loop 下次轮询（24h 内）→ honor toml 的 cup_honor.notification.channel_id 频道应收到 ExpiredHonorNoticeView embed
  7. winner_role 发放测试：赛季结束后，admin 手动到 Discord 身份组设置 → 给获胜方所有 supporter add winner_role（验证人工 7+7 流程 + admin 全权发放）

常见故障

按钮没反应
看 bot 日志是否报错；可能是 toml 加载失败或 channel_id 配错
Modal 提交失败
看 bot 日志确认 add_roles 抛了 Forbidden——bot 缺权限
自动补全不工作
需要先让 admin 在该 guild 跑过一次 /合战丨配置 上传配置，让 toml 被加载
用户已选 A 后想换 B
bot 设计为互斥——拒绝并不给用户暴露"联系管理组"。admin 手动 remove A 后用户重新点 B 即可
投稿时提示"黑/白名单"
检查 toml 对应 faction 的 submission_blacklist_role_ids / submission_whitelist_role_ids 配置
grant_honor 失败
json 里 honor_granted=false 表示失败。检查 honor toml 是否有对应 UUID 块
promotion 不 refresh
检查 promotion.refresh_minutes 是否合理；bot 重启后 tasks.loop 会从 0 开始计时；投稿期外 bot 不刷新
json 文件损坏
从 BACKUP_CHANNEL_ID 12h zip 备份还原
